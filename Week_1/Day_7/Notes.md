# Java Execution

## Question 1

> Explain the complete lifecycle of a Java program from
>
> HelloWorld.java
>
> to
>
> Output on Screen

---

1. The programmer writes Java source code in HelloWorld.java.
2. The Java compiler (javac) compiles the source code into platform-independent bytecode stored in HelloWorld.class.
3. The JVM's Class Loader loads the class into memory.
4. The Bytecode Verifier checks the bytecode for security and correctness.
5. The JVM allocates memory in the Runtime Data Areas (Heap, Stack, Method Area, etc.).
6. The Execution Engine executes the bytecode. Initially, the Interpreter executes it, while frequently executed code is compiled into native machine code by the JIT compiler.
7. The operating system executes the generated machine code, and the program displays "Hello World" on the screen.

## Question 2

> Why is Java platform independent?

---

Java is platform independent because its source code is compiled by the Java compiler (javac) into platform-independent bytecode (.class) instead of machine code. This bytecode can run on any operating system that has a compatible JVM. The JVM loads the bytecode and converts it into machine code suitable for the host operating system using its Execution Engine (Interpreter and JIT compiler). Since only the JVM is platform-specific while the bytecode remains the same, Java programs can run on multiple platforms without recompilation.

> What is Bytecode? Why does Java use it?

Bytecode is the platform-independent intermediate instruction set generated by the Java compiler (javac). It is stored in .class files and is executed by the JVM. Java uses bytecode so that the same compiled program can run on any operating system with a compatible JVM.

# Variables & Memory

How are primitive variables stored?
Primitive variables store the actual value directly. Their memory location depends on where they are declared. Local primitive variables are stored in the stack, instance primitive variables are stored inside objects in the heap, and static primitive variables are stored in the method area (or metaspace, depending on the JVM implementation).

How are objects stored?
Objects are created in the heap. A reference variable (usually stored on the stack if it is local) stores the memory reference of the object rather than the object itself.

When a method is called, the JVM creates a new stack frame on the call stack. This stack frame stores the method's parameters, local variables, operand stack, and return address. Program control transfers to the called method, suspending the caller. If another method is called, another stack frame is pushed onto the stack. Once the method finishes (either by reaching return or the closing brace for a void method), its stack frame is popped from the stack, and execution resumes at the saved return address in the calling method.

Arrays

> Explain how arrays work internally.

An array stores multiple elements of the same data type under a single name. In Java, an array is an object. When an array is created, the reference variable (if local) is stored in the stack, while the actual array object is allocated in the heap. The array elements are stored in contiguous memory locations, allowing efficient indexing. The array size is fixed during creation and cannot be changed later.

> Why does Java have ArrayList if arrays already exist?

Arrays are fixed in size and provide fast indexing but cannot grow after creation. ArrayList is a resizable array implementation that automatically creates a larger internal array and copies the existing elements whenever additional capacity is needed. It also provides many built-in methods such as add(), remove(), contains(), and size(), making it more convenient for dynamic collections.

> If methods didn't exist, how would software change?

If methods didn't exist, every program would have to be written inside a single block of code, such as main(). The same logic would need to be rewritten whenever it was required, leading to code duplication. Programs would become difficult to read, debug, test, and maintain. Reusing logic across different parts of the application would be almost impossible, making software development slower and more error-prone. Methods provide modularity, reusability, and better organization of code.

> Why is main() not enough?

main() is the entry point of a Java program, but it is not intended to contain all the program logic. While an entire program can technically be written inside main(), doing so would make the code difficult to read, debug, test, and maintain. Methods allow us to divide a program into smaller, reusable units, making the code modular and easier to manage.

> Why don't we store everything in Heap?

We don't store everything in the heap because accessing heap memory is slower and managing it is more expensive. The heap is designed for objects whose lifetime is not known in advance and is managed by the Garbage Collector. Simple data like local primitive variables, method parameters, and reference variables are short-lived, so storing them in the stack allows much faster allocation and automatic cleanup when a method finishes. Using the heap for everything would increase memory management overhead and reduce performance.

> Why don't we store everything in Stack?

We don't store everything in the stack because stack memory is limited and follows a Last-In-First-Out (LIFO) structure. Objects often need to survive after the method that created them returns or be shared between multiple methods or objects. If everything were stored in the stack, all objects would be destroyed as soon as their method ended, making it impossible to maintain data across method calls. The heap provides dynamic memory allocation for such long-lived objects.
